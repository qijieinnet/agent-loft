# 让已有专家成为个人 bot

建议把现有专家直接放进用户的「bot」联系人列表。每个用户可以添加多个 bot，同一专家在这个用户名下对应一个固定聊天。用户可以在 Web 找到它、在已绑定的飞书私聊继续交谈，也可以从 bot 入口查看交给它的定时任务和最近结果。引擎仍由专家配置决定，服务端在收到消息或任务到期时唤起执行器。增加一个联系人无需常驻一个进程。

## 把身份放在用户与专家的关系上

Grok Bot 的主 bot 可以主动联系用户，跨对话保留职责和工作摘要。OpenBot 可以让 Pi 与其他执行引擎共处同一工作区。对 agent-loft 更有价值的借鉴，是让用户能从同一个名字找回工作。现有专家已经定义提示词、模型、技能、MCP 和访问级别；共享专家的使用者还可以有自己的工具选择。（[Grok Bot 身份与记忆](https://docs.x.ai/grok-bot/bots) · [OpenBot 的 Pi 接入](https://openbot.run/providers/pi) · [专家访问规则](../src/core/experts.ts)）

首版按**使用者和专家**保存联系人，关联到该使用者拥有的一条 Web 会话。同一人从两台设备打开同一 bot，应得到相同会话；两个人添加同一共享专家，应各自得到私人会话、记忆和任务。每次启用或接续时检查账号、专家和引擎的可用性。失去权限时说明原因，由用户重新选择。移除 bot 会撤销事件监听并清除对应的事件记录。已有聊天和定时任务保留，可分别管理。（[会话归属](../src/core/personal.ts) · [Web 会话创建](../src/channels/web/api.ts)）

## 通过现有调度和推送交付第一版

用户在 Web 侧栏添加「NAS 管家」，也可以在已绑定的飞书私聊发送 `/bot`，选择同一联系人。之后两端都进入该 bot 已有的聊天。在选择、挂接、处理审批和投递后续事件时核验当期绑定，避免解绑后仍然向原聊天发送私人内容。任务结果的推送目的地仍由任务本身决定，和用户当前在哪个渠道聊天分别处理。（[飞书路由](../src/channels/feishu/bot.ts) · [任务推送](../src/channels/feishu/index.ts)）

比如用户对「NAS 管家」说“每周一早上检查备份，把异常发到飞书”。现有任务工具生成确认卡，用户确认时间、目标和推送设置后，由现有调度器运行。固定聊天可以承接结果；若用户选择让任务在专用会话执行，则记录该任务来自哪个 bot。bot 页面按用户及明确的关联列出任务，显示启停情况和最近运行状态。此前在其他项目中使用同名专家的任务，继续留在原来的项目里。（[任务工具](../src/core/tasks-bridge.ts) · [调度执行与中断处理](../src/core/task-runner.ts) · [任务数据](../src/core/tasks.ts)）

## 第二阶段：监听备份结果

当前「智能通知」在模型完成一轮后决定是否静默。若 NAS 一天检查很多次，过滤通知可以减少打扰，每次交给模型的检查仍会产生调用。OpenMausBot 提供了另一种做法：程序先读增量，按数据源的 ID 去重；有内容需要理解时，才合并为一轮模型调用。普通规则即可判断的会议提醒由服务直接生成。其每日简报在同一聊天中更新，新增待用户处理的事项才触发通知。（[现有静默判断](../src/core/hub.ts) · [OpenMausBot 主动例行任务](https://github.com/milind-soni/OpenMausBot/blob/main/docs/proactive-routines.md)）

已接入两种明确给出终态的来源。本机数据库每次实际备份发布一个带运行编号的结果，管理员可订阅。外部备份作业使用各监听独立的 Bearer 令牌提交结果；作业端负责在断线时保留未确认记录，恢复后携原运行编号重投。页面显示最后收到的上报时间，来源静默时没有新结论。接入示例见 [README](../README.md)。

程序按监听和运行编号识别重复失败，首次失败和最后上报状态在同一个 SQLite 事务中保存。用户可以只记入事件记录，也可以选择系统推送或本人绑定的飞书私聊。启用分析后，bot 在单独的私人聊天里给出排查建议。通知重试只处理投递，分析一旦派发就不自动重放。若在记录派发后突然断电，可打开该聊天继续。服务重启会接着处理待投递记录；网络在平台收件后、应答前中断时，仍可能收到重复通知。删除监听会撤销凭据并清理该监听的数据。（[事件存储](../src/core/bot-events.ts) · [投递与分析](../src/bot-event-runner.ts)）

## 用同一件交办验收跨端流程

| 场景 | 可观察的验收结果 |
|---|---|
| 同一用户双击、跨标签打开、刷新或重启后再打开 | 同一 bot 只对应一条有效固定会话 |
| 两名用户添加同一共享专家 | 每人只看见自己交办的任务、对话和结果 |
| 在 bot 里创建回到当前聊天的任务，再创建独立执行的任务 | 两项任务都能从该联系人找到，各自的执行和投递设置可查 |
| 在绑定私聊中使用 `/bot`，随后解除绑定 | 绑定时沿用 Web 对话；解绑后旧入口不能获得新的私聊内容 |
| 移除联系人、撤销专家共享、停用引擎 | 移除联系人保留历史与任务；撤权或引擎停用时应说明原因，禁止静默换用其他引擎 |

开发验证应覆盖 API 与持久化、前端入口、任务归属和飞书路由。发布前再用测试账号从真机完成一次创建任务、确认、收信、追问和解绑；模拟测试能证明服务端选对了目标，实际到达手机还取决于账号绑定、平台投递和设备权限。（[飞书处理](../src/channels/feishu/bot.ts) · [任务测试](../test/tasks.test.ts)）
